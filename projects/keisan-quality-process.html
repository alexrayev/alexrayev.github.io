KAK Development Process and Keisan Quality Metrics

A development process for a GUI team that blends Kaizen, Agile and RUP, plus an automated daily pipeline that measures software quality and publishes it to team dashboards.

Period2022 – present
My roleTechnical lead, process author
EmployerInfineon

The challenge

No single development process fit the team. Each one solves some problems and creates others, and none of them defined project requirements, quality metrics, continuing education or people performance clearly enough:

  • Agile: working software over documentation can leave a project without a solid architecture.
  • Kaizen: puts extra burden on lower-level management.
  • RUP: carries a fair amount of overhead and is less adaptive than Agile.
  • EVO: a long time from project start to a delivered solution.

The KAK process

I took the strongest practices from the three candidates (Waterfall and EVO were set aside), named the result KAK (Kaizen, Agile, RUP), and added a measurement layer called Keisan (計算, "calculation") and a learning practice called Library Day.

In use by the team

  • Team work and incremental changes
  • Points-based team velocity and iterative sprints
  • Post-activity reviews
  • Strong focus on requirements
  • Architecture-centric, component-based development
  • Quality and project metrics
  • Library Day after each iteration

Next steps

  • Standardized work
  • Human Performance Improvement (HPI): teamwork, workload, situation awareness and task-performance indicators, treated as a possible extension

Library Day

One day after each iteration for recommended topics, books, demos and possible new projects. It is how continuing education fits into the sprint rhythm.

Requirements structure

Requirements follow a fixed hierarchy that links the documentation tool to the issue tracker, so every task can be traced to the device and feature it serves.

Device
Top page: description, usage, register map and schematics. Tracked as a component.
Feature
Description and design tool. Tracked as an epic.
Widget
Sketch and component-to-register/command map. Tracked as a widget field.
Task
Story, improvement, task, bug or change request in the issue tracker.

Keisan: the automated quality pipeline

Keisan turns the process into numbers. A scheduled job runs every day on a Windows or Linux build server, with no manual steps, and refreshes the team's dashboards.

  1. Pull source: fetch the latest code from the Git repository and install dependencies.
  2. Run tests: run the unit tests with coverage and record the results.
  3. Scan: run static analysis (SonarQube) for bugs, vulnerabilities, code smells, duplication and complexity.
  4. Store: keep the results in PostgreSQL tables and views, so history is queryable.
  5. Export CSV: produce a current snapshot and a 180-day time series.
  6. Publish: upload both files to a Confluence page through its REST API, so the dashboards update themselves.

The dashboards combine pushed data with pulled data: sprint progression, created versus completed tasks, and project quality. A Grafana server complements them with delivered/failed tasks and project-quality charts, linked to the CI/CD tools (Jira, Jenkins and Bitbucket).

What it gave the team

  • One daily, objective view of quality and progress that anyone can open, with no extra reporting effort.
  • Trends over 180 days, so regressions in coverage, bugs or code smells show up early.
  • Quality metrics (test coverage, static analysis, guideline compliance and bug trends) that sit next to delivery metrics on the same pages.
  • A repeatable process other teams can adopt, with documentation, code reviews and SOLID design practices built in.
